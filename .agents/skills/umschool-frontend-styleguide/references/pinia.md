# Pinia

**1.** Не злоупотребляйте использованием хранилищ. Реактивные данные приложения должны находиться
как можно ближе к компонентам, которые их используют.

Проще говоря, выносите данные в хранилище только тогда, когда вам действительно необходимо:
- Упростить сложное общение между слабо связанными компонентами в рамках одной страницы приложения;
- Сделать состояние доступным на более, чем одной странице приложения;
- Закэшировать данные бэкенда.

Например, если какие-то данные используются только одним родительским и его дочерним компонентом - чаще всего,
реализовать их совместную работу с этими данными можно посредством простого общения через входные параметры и события, минуя хранилище.
Старайтесь задумываться об этом перед тем, как завести очередное поле в хранилище.

**2.** Используйте Composition API для определения хранилищ.

**3.** Используйте глаголы `fetch`, `create`, `delete` и `update` в именах типовых действий.

Данная таблица является скорее рекомендацией, нежели правилом, т.к. сложно подчинить 100% действий единому шаблону именования.

| Префиксный глагол | Когда использовать                                                                               |
|:-----------------:|--------------------------------------------------------------------------------------------------|
|       fetch       | Получение данных с бэкенда с их последующей записью в состояние                                  |
|      create       | Создание новой сущности на бэкенде с её последующей записью в состояние                          |
|      delete       | Удаление существующей сущности на бэкенде с её последующим удалением из состояния                |
|      update       | Обновление (PATCH/PUT) существующей сущности на бэкенде с её последующей перезаписью в состояние |

**4.** Функции хранилищ должны экспортироваться с именем, соответствующим шаблону
`use + <имя хранилища> + Store`.

```javascript
// Хорошо
export const useProductsStore = defineStore('products', () => {});
```

**5.** Изменяйте состояние хранилища напрямую без создания дополнительных функций-сеттеров.

**Почему:**
Изменение состояния в Vuex было невозможным без мутаций, ввиду чего у вас может возникнуть соблазн отразить эту
привычку и на Pinia. Однако, в Pinia вообще нет концепции “мутаций”, так что, на наш взгляд, дополнительное создание
функций-сеттеров для простого изменения состояния больше не имеет смысла.

```js [apples-store.js]
export const useApplesStore = defineStore('apples', () => {
  const apples = ref([]);

  // Бессмысленно - значение можно изменить из компонента и напрямую
  function setApples(apples) {
    apples.value = apples;
  }

  return { apples, setApples };
});
```

```vue [example.vue]
<template>
  <!-- Хорошо -->
  <AppleList v-model="applesStore.apples" />
</template>

<script setup>
  import { useApplesStore } from './apples-store';

  const applesStore = useApplesStore();

  // Хорошо
  applesStore.apples = ['Красное'];
</script>
```

**6.** Избегайте в действиях операций, которые не связаны с изменением состояния хранилища
напрямую. Вместо этого размещайте их в `watch()`, `$subscribe`, `$onAction` или используйте возможности компонентов.

**Почему:**
Целевая задача действий - реализация бизнес-логики, изменяющей состояние хранилища. Любые другие операции внутри
действий размывают их ответственность, усложняя понимание того, каким образом происходит обновление данных хранилища.

```javascript
export const useEchpochmakStore = defineStore('echpochmak', () => {
  const echpochmak = ref(null);

  async function fetchEchpochmak() {
    echpochmak.value = await echpochmakApi.getEchpochmak();

    // Плохо - прямые взаимодействия с UI в хранилище нежелательны
    Notify.success('Эчпочмак успешно загружен');

    // Плохо - операция не имеет прямого отношения к изменению состояния хранилища
    localStorage.setItem('echpochmak', JSON.stringify(echpochmak.value));
  }

  // Хорошо
  watch(echpochmak, () => {
    localStorage.setItem('echpochmak', JSON.stringify(echpochmak.value));
  });

  return { echpochmak, fetchEchpochmak };
});
```

**7.** Не создавайте геттеры с аргументами, если их вызов не приводит к кэшированию
результата. Используйте вместо этого действия.

```javascript
export const useUserStore = defineStore('user', () => {
  // Плохо - результат не закэшируется, использование computed не имеет смысла
  const getUserByIdBad = computed(() => (
    (userId) => users.value.find((user) => user.id === userId)
  ));

  // Хорошо
  function getUserByIdGood(userId) {
    return users.value.find((user) => user.id === userId);
  }

  // Допустимо - часть результата кэшируется
  const getActiveUserById = computed(() => {
    const activeUsers = users.value.filter((user) => user.active);

    return (userId) => activeUsers.find((user) => user.id === userId);
  });

  return { getUserByIdGood };
});
```

**8.** Используйте `kebab-case` в именах хранилищ.

```javascript
// Плохо
export const useUserSettingsStore = defineStore('userSettings', () => { });

// Хорошо
export const useUserSettingsStore = defineStore('user-settings', () => { });
```
