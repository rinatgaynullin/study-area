# i18n

**1.** Всегда вызывайте i18n для отображения текста вместо использования строковых литералов. Даже если в проекте всего одна локаль.

```vue
<template>
  <!-- Плохо -->
  Hello World

  <!-- Хорошо -->
  {{ t('hello_world') }}
</template>
```

**2.** Все переводы (даже используемые только в одном компоненте) должны размещаться в глобальных
JSON-файлах локалей.

**Почему:**
Vue-i18n позволяет использовать локализацию на базе компонентов, но такой подход добавляет ряд сложностей в
систематизации переводов, поэтому мы от него отказались.

**3.** Ключи переводов должны соответствовать стилю написания `lower_snake`.

```json
{
  // Плохо
  "helloWorld": "hello world",
  "Hello-World": "hello world",

  // Хорошо
  "hello_world": "hello world"
}
```

**4.** Ключи переводов должны быть переводом своего значения на английском языке.

> [!TIP]
> - В случае ключа для длинного значения допустимо использовать какое-то ёмкое сокращение с сохранением основной сути
>   оригинального текста (например, использовать первые слова текста или урезать предлоги, артикли и второстепенные слова).
> - Если же необходимо задать ключ для объемного текста, суть которого сложно выразить в сокращенном виде - только тогда,
>   в качестве исключения, допустимы абстрактные ключи вроде `about_company`.

```json
{
  // Ннебольшое словосочетание. Ключ - дословный перевод значения
  "chinese_new_year": "Китайский новый год",

  // Текст средней длины. Ключ - урезанная версия значения
  "i_am_adult_or_purchase_initiated_by_adults": "Мне есть 18 или покупку из моего аккаунта совершает родитель",

  // Объемный текст - допустима абстракция
  "about_company": "Что такое BlablaXDigital? Это вектор. И мы движемся вперед с 1996 года как в работе, так и просто по жизни. «BlablaXDigital» – аккредитованный ФНС, ПФ и Росстатом оператор электронного документооборота, сертифицированный EDI‑провайдер."
}
```

**5.** Таблицы переводов должны следовать максимально плоской структуре. Редкие вложенности допустимы, но лучше их избегать.

**Почему:**
Практика показывает, что создание абстрактных групп переводов со временем ведет к хаосу, поскольку они имеют свойство
быстро терять актуальность и сильно усложняют добавление новых переводов. Плоская структура - самый простой способ
борьбы с бессистемностью и дублированием в локалях.

```json
{
  // Точно не стоит
  "animals": {
    "cat": {
      "says": "Meow"
    },
    "dog": {
      "says": "Quack"
    }
  },

  // Изредка допустимо, но лучше избегать
  "page_titles": {
    "page_1": "Title1",
    "page_2": "Title2",
    "page_2": "Title2"
  },

  // То, что нужно
  "meow": "meow"
}
```

**6.** Значения ключей переводов должны начинаться с большой буквы.

**Почему:**
Условно говоря, в 80% UI-кейсов вам потребуется текст, начинающийся с большой буквы. Проще приводить первую
букву к верхнему регистру в 20% кейсов, чем совершать противоположную операцию в оставшихся 80%.

```json
{
  // Плохо
  "buy_now": "купить сейчас",

  // Хорошо
  "buy_now": "Купить сейчас"
}
```

**7.** Избегайте использования дублирующихся ключей для близких синонимов, старайтесь
вместо этого выражать тонкую разницу в значениях более точными ключами на английском языке.

```json
{
  // Плохо - попытка костыльного использования одного и того же ключа для двух синонимов
  "cool": "Круто",
  "cool_2": "Здорово",

  // Хорошо - ключи переводов явно выражают смысловое различие слов
  "cool": "Круто",
  "great": "Здорово"
}
```
