# Toast-нотификации

Всплывающее уведомление сообщает моментальную информацию или результат операции в ответ на действия пользователя, не
прерывая работу с интерфейсом. Служит механизмом обратной связи от системы и подтверждения действия пользователя. Например,
когда форма успешно заполнена и отправлена или возникли проблемы при загрузке файла и т.д.

> [!WARNING]
> Помните - любые UI-уведомления это аспект дизайна, поэтому первичным источником информации о целесообразности и
> наполнении какого-либо специфичного тоста являются макеты или личный диалог с дизайнером. Данный гайд предназначен для
> всех остальных уведомлений общего характера, не имеющих критического значения для UI/UX конкретной страницы. Проще
> говоря, руководствуйтесь представленными правилами только тогда, когда очевидно, что вмешательство дизайнера
> необязательно.

## Типы уведомлений

В нашей дизайн-системе используются 4 основных типа уведомлений, отличающихся иконкой. Тип уведомления определяется
характером отображаемого сообщения.

**Информационные уведомления**

   Используется для общих информационных сообщений. Cообщает дополнительную информацию, которая может не относиться к
   текущей задаче.

**Уведомления об успешном выполнении задачи**

   Сообщает пользователю, что система успешно выполнила действие. Не злоупотребляйте этим уведомлением. Не каждое действие
   нуждается в сообщении об успехе.

**Уведомления c предупреждением**

   Cообщает, что пользователь совершает действия, которые могут привести к ошибке или нежелательному результату. Привлекает
   внимание пользователя к возможной проблеме или для выполнения пользователем определенных действий.

**Уведомления c сообщением об ошибке**

   Информирует пользователей о том, что произошло что-то критическое и требует немедленного внимания. Сообщает об ошибке
   или каком-либо сбое в работе.

**1.** Не злоупотребляйте тостами: чем их меньше - тем лучше. Используйте их только
когда произошедшее событие неочевидно из UI.

> [!TIP]
> Тосты предназначены для ситуаций, когда нет возможности сообщить обратную связь в том месте экрана, где пользователь
> произвел действие, и где находится фокус его внимания.

**Плохо**

   - Использование тоста для подтверждения создания чего-либо, когда это действие приводит пользователя к UI с вновь созданным объектом.
     Например, при добавлении элемента в список или при автоматическом переходе на страницу редактирования новой сущности;
   - Использования тоста для подтверждения сохранения изменений чего-либо, когда режим просмотра изменяемого объекта и режим
     его редактирования имеют очевидную визуальную разницу. Например, если в режиме просмотра объект является карточкой со
     статичной информацией, а в режиме редактирования - формой с полями ввода. Возврат к состоянию просмотра является
     достаточным признаком того, что изменения были успешно отправлены.

**Хорошо**

   - Пользователь отправил документ из модального окна, окно закрылось - на странице отобразилось уведомление об успешной
     отправке;
   - Пользователь скопировал текст в буфер обмена посредством нажатия на специальную кнопку - на странице отобразилось
     уведомление о скопированном тексте.

**2.** Не пытайтесь заменить тостами UI-элементы и механизмы, которые лучше подходят
для решения определенных задач.

> [!TIP]
> Тосты следует использовать только для простых уведомлений и предупреждений с низким приоритетом, которые не должны
> блокировать взаимодействие пользователя с приложением. Для кейсов, требующих обязательного внимания пользователя, лучше
> подходят (например) модальные окна. Кроме того, не пытайтесь заменить тостами валидацию форм - для информирования
> пользователя о таких ошибках существуют другие специальные средства.

**3.** Не ставьте точку в конце текста уведомлений (касается и дополнительных подписей).

**4.** Для текста уведомлений успеха используйте форму:
`(опционально) существительное + глагол в прошедшем времени + (опционально) дополнительная информация`.

**Плохо**

   - Удалось!
   - Успех сохранения домашнего задания
   - Обновление пароля прошло успешно

**Хорошо**

   - Скопировано
   - Ответ сохранен
   - Файл загружен

**5.** Старайтесь сразу явно сообщать причину ошибки в тексте уведомлений об ошибке,
если это возможно. В обратном случае используйте форму:
`"Не удалось" + глагол совершенного вида (что сделать?) + существительное`.

> [!TIP]
> Если необходимо, подробности ошибки можно раскрыть в дополнительной подписи, но не более 1-2 коротких предложений.

**Плохо**

   - Ошибка загрузки данных
   - Не могу удалить запись
   - Что-то пошло не так
   - Не получилось скачать файл
   - Произошла непредвиденная ошибка
   - Произошла ошибка при загрузке чека

**Хорошо**

   - Файл слишком большой
   - Не удалось сохранить ответ
   - Не удалось загрузить профиль
   - Не удалось удалить домашнее задание
   - Не удалось обновить корзину
   - Не удалось обновить статус урока

**6.** Стремитесь к максимально лаконичному, но ясному тексту уведомлений.

**Почему:**
Тост появляется только на несколько секунд в крошечном контейнере. Это означает, что говорить в этот момент нужно как
можно меньше. Лучший способ быть кратким в таких условиях  - избегать любых слов, не несущих принципиального значения
для смысла сообщения. Правильные уведомления состоят из коротких утверждений, а не из предложений.

**Плохо**

   - Пароль вашего аккаунта успешно обновлен

**Хорошо**

   - Пароль обновлен

**7.** Старайтесь использовать "общий язык" в подтверждениях и уведомлениях об ошибках.

**Почему:**
Этот подход упрощает локализацию, а также уменьшает необходимость написания множества различных версий уведомлений для
схожих вариантов использования. Обычно нет необходимости включать в текст уведомления конкретные имена сущностей/файлов/страниц,
поскольку пользователь может получить этот контекст и из других мест в UI.

**Плохо**

  - Не удалось сохранить ответ на домашнее задание по теме "Дрочим без рук"

**Хорошо**

  - Не удалось сохранить ответ

**8.** Старайтесь избегать одновременного отображения нескольких
однородных тостов.

**Почему:**
Несмотря на то, что тосты не так "агрессивны", как модальные окна, они все равно отвлекают внимание пользователя. Частые
прерывания мешают удобству использования, особенно для людей с нарушениями зрения и когнитивных функций. Как правило,
пользователю не нужна детальная информация о всех нюансах цепочки произошедших событий.

Кейс 1 - Произошли ошибки нескольких запросов, от которых зависит первичное отображение страницы

**Плохо**

     Одновременно:
   - Не удалось загрузить профиль
   - Не удалось загрузить уроки
   - Не удалось загрузить статус домашнего задания

**Хорошо**

  - Не удалось загрузить данные страницы

Кейс 2 - Для сохранения данных формы в силу специфичной логики совершается несколько разных запросов

**Плохо**

     Одновременно:
  - Профиль обновлен
  - Цели сохранены
  - Пользовательские настройки обновлены

**Хорошо**

  - Личные данные обновлены

**9.** Используйте существующие ключи i18n с готовыми шаблонами сообщений, если это
возможно.

```json [ru.json]
{
   // Плохо
   "failed_to_update_profile": "Не удалось обновить профиль",

   // Хорошо
   "failed_to_update": "Не удалось обновить",
   "failed_to_update_profile": "@:failed_to_update профиль"
}
```

**10.** Используйте обращение на ТЫ в сообщениях уведомлений.

**Плохо**

  - Попробуйте перезагрузить страницу

**Хорошо**

  - Попробуй перезагрузить страницу
