# Архитектура

**1.** Имена всех файлов в проекте должны соответствовать стилю написания `kebab-case`.

**2.** Обращайтесь "от лица системы" при именовании чего-либо.

```ts [entities/lesson/api/lessons-api.ts]
export const lessonsApi = {
  // Плохо - местоимение "my" это обращение от лица пользователя
  getMyLessons: () => {
    // ...
  },

  // Хорошо - обращение от лица системы
  getUserLessons: () => {
    // ...
  },
};
```

**3.** Именуйте файлы модулей с одним экспортом так же, как и экспортируемую ими
функциональность.

```js [download-file.js]
export const downloadFile = (url) => {
  // ...
};
```

```ts [use-product-store.js]
export const useProductStore = () => {
  // ...
};
```

```ts [user-statuses.ts]
export const USER_STATUSES = [
    /// ,,,
] as const;
```

**4.** Используйте шаблон именования `<имя> + Api` для имен http-сервисов.

```javascript [examples-api.js]
// Хорошо
export const examplesApi = {
  getExamples: () => { /* ... */ },
  postExample: () => { /* ... */ },
};
```

## Feature-Sliced Design

> [!IMPORTANT]
> Данная секция связана с использованием методологии Feature-Sliced Design версии 2.1+. Пожалуйста, внимательно
> ознакомьтесь с официальной документацией FSD прежде чем
> продолжить чтение.

**5.** Следуйте архитектуре FSD во всех приложениях, вне зависимости от их назначения, размера и
физического расположения (репозитория).

**6.** Размещайте общую функциональность монорепозитория (необходимую нескольким
приложениям или пакетам) в папке `repository/layers` организованной по принципам FSD.

**7.** Импортирование базовых страниц из других расширяющих их страниц разрешено.

Бывают ситуации, когда (например) в нескольких приложения монорепозитория необходимо реализовать одну и ту же страницу
с незначительными различиями в текстовых формулировках, элементах управления и т.п. Как правило, легче всего сделать это
созданием в `layers` общей "базовой" страницы, которая может быть расширена в конкретном приложении через публичный API
компонента. Однако, поскольку страница является самой верхнеуровневой из структурных абстракций FSD, "горизонтальное"
импортирование слайса страницы из слайса другой страницы в таких ситуациях становится неизбежным.

Кейс достаточно редкий для фронтенда в целом, но крайне характерный для фронтенда Умскула.

```vue [layers/pages/catalog/ui/catalog.vue]
<!-- Базовая страница каталога -->

<template>
  <div>
    <h1>{{ props.title }}</h1>

    <div>
      <div>Продукт 1</div>
      <div>Продукт 2</div>
    </div>

    <div
      v-if="$slots.footer"
      class="mt-2"
    >
      <slot name="footer" />
    </div>
  </div>
</template>

<script setup lang="ts">
const props = withDefaults(defineProps<{
  title?: string,
}>(), {
 title: 'Каталог',
});
</script>
```

```vue [apps/platform-ru/src/pages/catalog/ui/catalog.vue]
<!-- Расширение базовой страницы каталога в конкретном приложении -->

<template>
  <Catalog title="Магазин">
    <template #footer>
      <div>Акция! Купи 3 по цене 1!</div>
    </template>
  </Catalog>
</template>

<script setup lang="ts">
// Допустимо - страница расширяет базовую страницу из layers
import { Catalog } from '@monorepo/layers/pages/catalog';

// Всё еще запрещено в соответствии с правилами импортов в FSD
import { FeedbackForm } from 'pages/lesson';
import { useHomeworkStore } from '@monorepo/layers/pages/homework';
</script>
```

**8.** Сегменты слайсов выражают вертикальные срезы функциональности, а не горизонтальные.

> [!NOTE]
> Это не локальное соглашение нашей команды, а фундаментальный принцип FSD, который не совсем прозрачно описывается
> официальной документацией и многим неочевиден.

Важно понимать, что сегменты в FSD объединяют в себе файлы по **ответственности**, а не по типу. Это означает, что
вне зависимости от того, является ли какой-то модуль утилитой/константой/TS-типом: если он используется только в
контексте рендеринга - он должен лежать в сегменте `ui`, если в контексте общения с бэкендом - в сегменте `api` и т.д.

```
features/select-country
├─ ui
│  ├─ country-flag-icon.vue
│  ├─ get-country-flag-url-by-code.ts - Хорошо, функция относится только к рендерингу, это НЕ lib
│  └─ country-flag-icon-props.ts - Хорошо, это тип относящийся только к компоненту
├─ config
│  ├─ api-types.ts - Плохо, типы бэкенда относятся к сегменту api
│  └─ country-select-options.ts - Плохо, массив опций селекта относится к рендерингу (сегменту ui)
```

**9.** Не размещайте в сегменте `lib` какого-либо слайса код связанный с бизнес-логикой.

> [!NOTE]
> Официальная документация FSD актуальной версии менее категорична в этом отношении, но, на наш взгляд, границы
> ответственности `lib` должны быть определены более строго.

Если говорить проще: сегмент `lib` не должен знать об "уроках", "домашних заданиях", "учителях" и любых других сущностях
Умскула. Его задача - предоставлять универсальную служебную функциональность, не зависящую от специфики конкретного
бизнеса. Например - чистые утилитарные функции (аналогичные lodash), SDK для внешних сервисов веб-аналитики, локальные
библиотеки для работы с цветом/звуком/файлами и т.п.

Относитесь к `lib` как к публичным npm-пакетам, только на локальном уровне.

```
features/save-homework-answer
├─ lib
│  ├─ is-homework-done.ts - Плохо: код связанный с бизнес-сущностью homework
│  ├─ capitalize-string.ts - Хорошо: чистая функция ничего не знающая об Умскуле
│  └─ ya-metrika-sdk.ts - Хорошо: локальная библиотека для работы с внешним сервисом
```

**10.** Не занимайтесь преждевременной декомпозицией чего-либо на слайсы,
старайтесь переносить часть слайса на нижележащий слой только в случае необходимости повторного использования этой
функциональности в других слайсах.

> [!NOTE]
> Предыдущая версия FSD требовала воспринимать приложение как набор атомарных фич и декомпозировать страницы на кучу
> мелких слайов, однако, в версии 2.1 это поменялось на подход pages-first,
> и теперь страница - главный структурный элемент приложения, а все нижележащие слои предназначены для переиспользования
> кода. Такое изменение парадигмы кажется логичным и нам.

> [!IMPORTANT]
> Допустимы исключения для слоя `widgets` - если это упрощает восприятие конкретной страницы, разрешается вынос блока
> её функциональности в виджет даже если он используется только на одной странице.

**11.** Используйте фича-флаги и `platformType`
преимущественно на слоях `app` и `pages`. Если это физически возможно, не обращайтесь к ним напрямую на слоях
`widgets`, `features`, `entities` и `shared`.

| Слой | Правило |
| --- | --- |
| `app` | Используйте флаги и `platformType` для конфигурации приложения, провайдеров и маршрутизации. |
| `pages` | Используйте флаги и `platformType` при композиции страницы и передавайте результат проверки ниже. |
| `widgets`, `features`, `entities`, `shared` | Получайте уже вычисленные значения через параметры, props или зависимости публичного API. |

**Почему:**
Прямое чтение флагов или `platformType` связывает нижние слои с конфигурацией конкретного приложения и затрудняет их
переиспользование. Верхний слой должен выбрать реализацию или вычислить нужное состояние, а нижний — получить явное
значение, не зная, каким флагом или типом платформы оно определяется.

Если проверку невозможно поднять на `app` или `pages`, разместите её на самом верхнем из доступных слоёв и явно
зафиксируйте причину исключения в коде.

**12.** Именуйте модули слайса соответственно уровню абстракции - емко для
локального использования и детализировано для публичного API слайса.

> [!IMPORTANT]
> При этом, даже локальные имена компонентов слайсов должны удовлетворять нашей общей [конвенции именования](./vue.md#component-naming)

Нет нужды нагружать локальные имена модулей слайса (например, компонентов) всей предметной информацией, которая и так
очевидна из имени/назначения слайса - это лишь бессмысленно продублирует в именах контекст, за актуальностью которого
придется дополнительно следить (например, если слайс переименуется или незначительно изменит концепцию - придется также
переименовывать все включенные в него модули). Однако, при экспорте из слайса имя публичного модуля должно включать
в себя полный контекст, чтобы внешний код однозначно понимал "с чем имеет дело".

```ts [widgets/bonus-course-lesson-card/index.ts]
// Хорошо
export { LessonCard as BonusCourseLessonCard } from './ui';
```

**13.** Именуйте фичи "глагольно" - так, чтобы их имена отвечали на вопрос
"что сделать?".

> [!TIP]
> Правило не распространяется на имена групп фичей

```
Плохо:
- payment
- lesson-list
- profile-update

Хорошо:
- update-profile
- add-product-to-card
- change-theme
```

**14.** Избегайте использования `*` при реэкспортах в index-файлах слайсов.

**Почему:**
Это нарушает принцип публичного API модулей в FSD - реэкспортируя из сегмента всё, можно случайно открыть
публичный доступ к внутренним модулям слайса, т.е. нарушить сокрытие деталей его реализации.

```ts [entities/user/index.ts]
// Плохо
export * from './ui';
export * from './model';

// Хорошо
export { useUserStore } from './model';
export { UserCard, UserCardAvatar } from './ui';
```

**15.** Импорты типов сущностей из других сущностей разрешены.

**Почему:**
Фактическая зависимость сущности от типов другой сущности встречается достаточно часто, и официальная
документация FSD предлагает несколько путей решения этой проблемы - например, хранение всех типов бэкенда в слое `shared`
или использование для импортов специальной `@x`-нотации. Все эти варианты показались нам неудобными и мы решили
просто слегка модифицировать правило импорта FSD на уровне команды.

**16.** Размещайте api-сервисы и все порождаемые ими типы как можно
ближе к месту их использования в сегменте `api`.

Формулировка "как можно ближе" означает "настолько близко, насколько позволяют правила импорта FSD". Если
какой-то бэкенд и его типы используются только одной сущностью или фичей - логично, что они должны быть расположены в
сегменте `api` этого слайса.

Также важно уточнить, что мы НЕ выделяем типы сущностей бэкенда (интерфейс `User` в примере) в какую-то отдельную
категорию и храним их в сегменте `api` вместе со всеми остальными типами порождаемыми бэкендом.

```ts [entities/user/api/types.ts]
export type UserId = string;

interface User {
  id: UserId,
  name: string,
}

export interface GetUserResponseBody {
  data: User
}
```

```ts [entities/user/api/user-api.ts]
import type { UserId, GetUserResponseBody } from './types';

export const getUser = (userId: UserId): Promise<GetUserResponseBody> => {
  // ...
};
```

**17.** Размещайте всю функциональность, запускаемую на этапе инициализации приложения, в
нестандартном сегменте `app/boot`.

> [!TIP]
> Чаще всего такой функциональностью является всё то, что обычно необходимо вызывать в `main.ts`

Как правило, еще до первой отрисовки, большинству фронтенд-приложений необходимо предварительно произвести ряд
подготовительных операций: настройку библиотек, инициализацию аналитики, получение каких-то базовых данных с бэкенда
и т.п.

Мы подглядели идею boot-files у Quasar и договорились размещать такую
функциональность в специальных модулях, которые мы называем "загрузочными файлами".
